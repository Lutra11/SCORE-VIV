# SCORE-VIV 统一实验配置与正式结果协议

> 文档状态：`ACTIVE`  
> 协议版本：`1.0.0`  
> 生效日期：`2026-11-04`  
> 适用范围：`experiments/E1_*` 至 `experiments/E9_*`  
> 规范关键词：**必须**表示强制要求，**建议**表示默认做法，偏离时必须说明理由。

## 1. 目的与效力

本文件是 SCORE-VIV 项目所有后续实验的统一执行协议，固定独立运行次数、随机种子、数据隔离、预算核算、统计报告、结果保存和正式结果准入规则。

各实验的 YAML 可以增加模块专属参数，但不得静默覆盖本协议。确需修改正式规则时，必须：

1. 在查看该批正式结果之前修改本文件并提升协议版本；
2. 在实验配置中记录偏离项、原因和批准日期；
3. 使用新的结果批次标识，不得与旧协议结果混合统计。

## 2. 三类运行等级

| 等级 | 固定重复次数 | 用途 | 能否进入论文正式结果 |
|---|---:|---|---|
| `smoke` | 3 | 检查接口、单位、依赖、输出和流程 | 否 |
| `pilot` | 10 | 调参、预算摸底、发现数值问题 | 否 |
| `formal` | 按第 4 节 | 锁定配置后的正式实验 | 是，但仍须通过第 11 节准入检查 |

规则如下：

- `smoke`、`pilot` 和 `formal` 必须使用不同种子，结果不得合并。
- 所有超参数、停止条件和评价指标必须在启动 `formal` 前冻结。
- 查看正式测试集或正式种子结果后，不得据此调参；如确需修改，原批次作废并以新协议版本和新批次重新运行全部比较方法。
- `formal` 不是文件名标签。缺少规定重复数、必要输入或独立验证时，即使目录名含 `formal` 也不得作为正式结果。

## 3. 统一随机种子协议

### 3.1 实验种子块

每类实验占用一个互不重叠的 10,000 整数种子块：

| 实验 | 种子块 | `smoke` | `pilot` | `formal` 主区间 | 独立验证区间 |
|---|---:|---:|---:|---:|---:|
| E1 | 110000–119999 | 110000–110002 | 110100–110109 | 111000–118999 | 119000–119999 |
| E2 | 120000–129999 | 120000–120002 | 120100–120109 | 121000–128999 | 129000–129999 |
| E3 | 130000–139999 | 130000–130002 | 130100–130109 | 131000–138999 | 139000–139999 |
| E4 | 140000–149999 | 140000–140002 | 140100–140109 | 141000–148999 | 149000–149999 |
| E5 | 150000–159999 | 150000–150002 | 150100–150109 | 151000–158999 | 159000–159999 |
| E6 | 160000–169999 | 160000–160002 | 160100–160109 | 161000–168999 | 169000–169999 |
| E7 | 170000–179999 | 170000–170002 | 170100–170109 | 171000–178999 | 179000–179999 |
| E8 | 180000–189999 | 180000–180002 | 180100–180109 | 181000–188999 | 189000–189999 |
| E9 | 190000–199999 | 190000–190002 | 190100–190109 | 191000–198999 | 199000–199999 |

正式运行默认从主区间首个种子开始连续取值。例如 E7 的 30 次正式优化使用 `171000–171029`。不得为了得到更好结果而跳过或替换种子。

### 3.2 子随机流

每次运行的表中种子是 `run_seed`。数据生成、数据划分、算法初始化、环境抽样、估计器噪声和独立验证不得共用一个顺序推进的随机数流。后续代码统一按下列流编号派生：

| `stream_id` | 随机流 |
|---:|---|
| 10 | 数据设计或样本生成 |
| 20 | 训练/验证/测试划分 |
| 30 | 优化器初始种群或初始解 |
| 40 | 环境与不确定性样本 |
| 50 | 概率估计器、测量或噪声模拟 |
| 60 | Bootstrap/统计重采样 |
| 90 | 独立高精度复核 |

推荐实现为 `numpy.random.SeedSequence([run_seed, stream_id])`。禁止使用 Python 的 `hash()` 派生种子，因为其结果可能跨进程变化。

### 3.3 公共随机数

- 同一算例中比较不同算法或消融版本时，必须按重复编号使用相同 `run_seed`、相同环境样本和相同允许的初始候选集。
- 方法内部额外随机性必须来自独立子随机流。
- 公共随机数用于降低比较方差，不意味着训练数据可以与独立测试或独立复核数据共享。

## 4. E1–E9 正式实验强度

| 实验 | 正式实验最低要求 | 正式种子/重复规则 |
|---|---|---|
| E1 FEM/VIV 验证 | 每个确定性基准工况运行一次；网格收敛至少 4 个网格层级；覆盖计划中全部 Xu 2023 验证工况 | 确定性计算记录 `111000`；若含随机测量/Bootstrap，执行 30 次 `111000–111029` |
| E2 冲刷验证 | 全部预先声明的 Yu 2024 校准和独立验证工况；校准集与验证集隔离 | 确定性拟合记录 `121000`；随机初始化或不确定性拟合执行 30 次 `121000–121029` |
| E3 冲刷–FEM–VIV 耦合 | 每个预先声明的确定性演化工况运行一次；不确定性情景按独立环境实现重复 | 确定性计算记录 `131000`；随机情景 30 次 `131000–131029` |
| E4 疲劳验证 | 每条实测或已验证应力历程运行一次；随机谱/随机环境下每个工况 30 条独立历程 | `141000–141029`；合成历程不得替代正式实测验证 |
| E5 多保真代理 | 锁定独立测试集；30 次独立训练设计/初始化；每次报告测试集误差和区间校准 | `151000–151029`；测试集使用独立验证流且不得参与选模 |
| E6 可靠性与 NA-QAE | 每个“方法 × 目标概率 × 噪声水平 × 预算”组合 200 次独立重复 | `161000–161199`；不同方法按重复编号配对 |
| E7 治理优化 | 每个“算法 × 基准算例”30 次独立优化，并对每次最终候选做独立可靠性复核 | `171000–171029`；独立复核由 `stream_id=90` 派生 |
| E8 消融 | 估计器级消融每个组合 200 次；完整优化器级消融每个“版本 × 算例”30 次 | 估计器级 `181000–181199`；优化器级 `182000–182029` |
| E9 敏感性 | Sobol 基础样本量从 2048 起；用 `N/2` 与 `N` 检查排序稳定性；95% 区间采用 1000 次 Bootstrap；随机稳健性情景 30 次 | 主种子 `191000`；Bootstrap 用流 60；随机情景 `191000–191029` |

以上为最低强度，不得因部分任务失败而降低分母。增加重复数必须对所有被比较方法对称执行，并在运行前写入配置。

## 5. 数据划分与信息隔离

- 参数标定、模型选择和最终验证必须使用互斥数据。
- E1/E2/E4 的公开试验数据必须按物理工况或试验组划分，禁止把同一时序或同一试验的相邻点随机拆入训练集和测试集。
- E5 必须保留锁定的独立测试集。若使用已有有限数据，默认按物理组划分约 `60%/20%/20%` 的训练/验证/测试；若可生成 HF 数据，则测试集应单独设计和生成。
- 代理模型主动学习只能访问训练池和验证指标，不能查询正式测试标签。
- E7 最终方案必须使用与优化阶段不同的独立环境样本和高精度模型复核。
- 所有输入数据必须记录来源、版本、单位、预处理脚本和 SHA-256 哈希。

## 6. 统一预算与公平比较

### 6.1 预算必须同时记录

每次运行至少记录：

1. LF、MF、HF/物理模型调用次数；
2. 可靠性样本数；
3. Oracle 查询次数；
4. 优化目标/约束评价次数；
5. 峰值内存和实际运行时间；
6. 终止原因以及是否触及预算上限。

### 6.2 Oracle 查询口径

- Direct MC 的一次失效指示函数评价计为 1 次 Oracle 查询。
- 对 Grover 深度 `m`、测量次数 `shots` 的 QAE 模拟，统一计为
  `oracle_queries = shots × (2m + 1)`。
- 多深度、多轮自适应预算的总查询数必须对所有深度和所有轮次求和，不得只报告 `shots` 或最大一轮预算。
- 经典模拟中的矩阵运算时间和 Oracle 查询复杂度分别报告；不得由模拟查询数直接声称真实量子硬件加速。

### 6.3 比较规则

- E6 以 Oracle 查询上限为主要公平预算，初始测量预算 `2048`、最大预算 `8192` 作为默认预算档，同时必须报告估计误差和区间覆盖率。
- E7/E8 优化比较以物理/HF 调用或预先声明的统一目标评价上限为主要预算；种群规模、停止条件和独立验证规则必须一致。
- 运行时间只能作为次要工程指标，因为 GitHub 托管 runner 的负载不可控。正式计时应记录 runner 操作系统、CPU、Python 和依赖版本。
- 未实现等价预算核算的方法不得进入“更高效”结论。

## 7. 停止、失败和重跑规则

- 所有停止条件必须在正式运行前写入 YAML，包括最大评价数、最大迭代数、容差和预算上限。
- 不能以“得到满意结果”为停止条件，也不得在不同方法间使用不同的隐藏提前停止规则。
- 数值失败、不可行、超时和异常均属于实验结果，必须记录并计入总运行数。
- 只有明确的基础设施故障（例如 runner 中断、artifact 上传失败）允许使用**相同种子和相同配置**重跑；旧日志必须保留。
- 算法失败不得更换为备用种子。修复算法后必须提升代码或配置版本，并重跑该比较组的全部方法。

## 8. 统计报告约定

- 所有随机实验同时报告：有效运行数/计划运行数、均值、标准差、中位数、IQR、最小值、最大值和 95% Bootstrap 置信区间。
- E6/E8 估计器实验必须报告偏差、MAE、RMSE、相对误差、95% 区间覆盖率、平均区间宽度和 Oracle 查询数。
- E7 优化实验必须报告最优可行成本、可行运行比例、失效概率、治理措施数量、收敛历史、HF 调用数、Oracle 查询数和独立复核通过率。
- 方法比较基于同一重复编号的配对差值；默认采用双侧 Wilcoxon signed-rank 检验，显著性水平 `α=0.05`，多重比较使用 Holm 校正。
- 显著性检验必须与效应量和置信区间同时报告，不得只报告 `p` 值。
- 正式汇总不得删除离群种子；若确认实现错误，按第 7 节处理整个比较组。

## 9. 统一配置快照

后续各实验 YAML 至少应能映射到以下公共字段；在代码尚未统一前，本节作为规范源：

```yaml
protocol:
  name: SCORE-VIV-EXPERIMENT-PROTOCOL
  version: 1.0.0
  level: formal                 # smoke | pilot | formal
  locked: true

reproducibility:
  seed_policy: experiment-block-v1
  common_random_numbers: true
  record_git_commit: true
  record_environment: true
  hash_algorithm: sha256

statistics:
  confidence_level: 0.95
  alpha: 0.05
  bootstrap_resamples: 10000
  multiple_comparison: holm

qae_budget:
  initial_shots: 2048
  max_shots: 8192
  oracle_query_rule: "sum(shots * (2*m + 1))"

result_policy:
  keep_failed_runs: true
  replace_failed_seed: false
  independent_final_validation: true
```

实验专属 YAML 还必须显式写入 `experiment_id`、`case_id`、`method_id`、`run_seed` 或种子列表、`independent_runs/repetitions`、输入清单、主要预算、停止条件和输出目录。

## 10. 输出目录与必存文件

正式结果建议写入以下结构，GitHub Actions artifact 保持同样层次：

```text
outputs/<batch_id>/<experiment_id>/<case_id>/<method_id>/seed_<run_seed>/
├── config.snapshot.yaml
├── metadata.json
├── environment-lock.txt
├── input-manifest.json
├── metrics.json
├── history.csv
├── run.log
└── checkpoints/
```

其中：

- `batch_id` 建议为 `formal-YYYYMMDD-protocol-v1.0.0-<git_short_sha>`；
- `metadata.json` 必须记录协议版本、Git commit、工作树状态、时间、seed、stream 规则、平台和终止原因；
- `input-manifest.json` 必须记录所有输入路径、SHA-256、单位和来源；
- 聚合结果必须从各 seed 原始文件自动生成，不得手工改写；
- GitHub Actions 的短期 artifact 不是永久归档。正式批次必须在保留期内下载到 `github-outputs/<batch_id>/`，并保留校验清单。

## 11. 正式结果准入检查

一批结果只有同时满足以下条件，才可以标记为“正式论文结果”：

- [ ] 使用本协议的当前有效版本，且配置在运行前已锁定；
- [ ] 实验前置条件已完成，例如 E7 只能使用通过验证的 E1–E6 模块；
- [ ] 单元测试、集成测试和配置校验全部通过；
- [ ] 不含 `TBD`、未声明默认参数、占位数据或未披露的代理指标；
- [ ] E1/E2/E4 使用正确的公开数据、尺度、单位和独立验证工况；
- [ ] 达到第 4 节规定的样本量，失败运行没有被静默删除或替换；
- [ ] 所有对比方法使用相同案例、种子、预算口径和停止规则；
- [ ] E6/E8 使用正确的 Oracle 查询累计公式；
- [ ] E7 的可行性方向、可靠性阈值和最终独立复核均通过测试；
- [ ] 保存配置快照、代码版本、环境、输入哈希、日志和逐次结果；
- [ ] 汇总统计能够由原始结果一键重建；
- [ ] 结论只覆盖真实完成并通过检查的实验，不将 `smoke`/`pilot` 或合成代理结果冒充正式证据。

任一项不满足时，结果只能标记为 `development`、`pilot` 或 `blocked`，不得进入论文主结果表。
